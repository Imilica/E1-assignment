# Test Plan

Source: [requirements/Sandbox_Requirements.pdf](../requirements/Sandbox_Requirements.pdf). Conventions: [rules.md](rules.md) (Playwright + TypeScript, POM, `getByTestId`, seeded faker factories, Chromium, UI only).

## 1. Scope

| Feature | In scope | Out of scope |
|---|---|---|
| Login | Email/password login, redirect, error on failure, Remember me, Forgot Password / Admin / Login links, frontend validation, masked password, HTTPS, labels/placeholders | Forgot-password and admin-login page internals (link navigation only), account lockout (not in the PDF) |
| New Test Case | Create with required/optional fields, multiple ordered steps, Automated toggle, validation errors, Enter-key behaviour, Back arrow, saved case appears in the list | Editing/deleting test cases, list filtering/sorting |

## 2. Assumptions and open questions

1. **Account lockout is not in the PDF.** Brute-force locking is therefore not planned as a test.
2. The PDF does not give exact error texts, routes, or the "longer period" for Remember me. Tests assert on a visible error element (test id) and the URL pattern; exact copy and routes must be confirmed against the app.
3. Test ids already exist in the app and are listed in section 6; add new ones only where missing (rules.md §3).
4. Valid credentials are supplied through `USER_EMAIL` / `USER_PASSWORD`; an invalid-credential pair is generated by `userFactory`.
5. "Remember me keeps the user logged in for longer" is verified by cookie expiry (persistent vs session cookie), because a real long wait is not practical.

## 3. Test environment

- Browser: Chromium, fresh context per test; login tests run unauthenticated, test-case tests reuse `storageState` from a setup project.
- Data: seeded `@faker-js/faker` factories (`FAKER_SEED`), unique titles per test.
- Reports: Playwright HTML in `reports/html` (local).

## 5. Detailed test cases

### Login

**TC-LOGIN-01: Successful login redirects to dashboard** (P1)
- Preconditions: user is logged out; valid credentials from env.
- Steps: open `/login`; fill email and password; click Login.
- Expected: URL matches the dashboard route; no error message is visible.

**TC-LOGIN-02: Invalid credentials show an error** (P1)
- Data: `userFactory()` random email/password (well-formed but unknown), plus a valid email with a wrong password.
- Steps: submit the login form.
- Expected: error message visible; URL stays on login; email field keeps its value; password is not exposed.

**TC-LOGIN-03: Empty fields trigger frontend validation, no backend call** (P1)
- Cases: both empty; email only; password only.
- Steps: register a request listener for the login API; click Login.
- Expected: field-level error messages shown for the empty field(s); **no** login request is sent; URL unchanged.

**TC-LOGIN-04: Invalid email formats are rejected** (P2, data-driven)
- Data table: `plainaddress`, `user@`, `@domain.com`, `user@domain`, `user name@domain.com`.
- Steps: enter the email with a valid password; submit.
- Expected: email validation error shown for each; no login request is sent.

**TC-LOGIN-05: Password masked and HTTPS only** (P1)
- Steps: open login page; type into password.
- Expected: password input has `type="password"`; page URL starts with `https://`; an `http://` request to the page is redirected to HTTPS or refused.

**TC-LOGIN-06: Remember me keeps the user logged in longer** (P2)
- Steps: log in with Remember me ON; in a second run log in with it OFF; inspect auth cookie/storage.
- Expected: toggle is unchecked by default; with ON the auth cookie is persistent (has an `expires` date later than a session cookie); with OFF it is a session cookie.

**TC-LOGIN-07: Navigation links** (P2)
- Steps / Expected: Forgot Password link goes to the forgot password page; Admin link in the top menu goes to the admin login page; Login link in the top menu goes to `/login` or stays on it when already there.

**TC-LOGIN-08: Labels, placeholders and toggle visibility** (P3)
- Expected: email and password inputs have placeholders "Email" and "Password" and clear labels; the Remember me toggle is visible and enabled.

### New Test Case

Preconditions for all: user is logged in (shared `storageState`); user opens the New Test Case page.

**TC-NTC-01: Create with all fields and see it in the list** (P1)
- Data: `testCaseFactory()` with title, description, expected result, 3 steps, Automated ON.
- Steps: fill all fields, add steps, toggle Automated, Submit.
- Expected: user lands on (or can open) the Test Case List; a row with the generated title exists and shows the entered data.

**TC-NTC-02: Create with required fields only** (P1)
- Data: factory with `description` omitted, 1 step.
- Expected: saved successfully; appears in the list.

**TC-NTC-03: Required fields empty** (P1, data-driven)
- Cases: empty Title; empty Expected Result; both empty; all empty. Each override changes only the field under test.
- Steps: Submit.
- Expected: error message shown next to each empty required field; nothing is added to the list (list count unchanged).

**TC-NTC-04: At least one step required** (P1)
- Data: valid Title and Expected Result, step left empty.
- Expected: step error shown; test case not saved.

**TC-NTC-05: Multiple steps keep their order** (P1)
- Data: 5 distinct ordered steps.
- Steps: click Add Test Step 4 times, fill each in order, Submit, open the saved test case.
- Expected: steps appear in the same order they were entered, both before submit and after save.

**TC-NTC-06: Automated toggle** (P2)
- Expected: toggle is off by default; when turned on before Submit, the saved test case shows Automated; when left off, it shows not automated.

**TC-NTC-07: Enter key does not submit an invalid form** (P2)
- Steps: with required fields empty or partly filled, press Enter in Title and in a step field.
- Expected: form is not submitted and nothing is saved. With all fields valid the behaviour is allowed to submit (observed and recorded).

**TC-NTC-08: Back arrow** (P2)
- Steps: fill some fields; click the back arrow.
- Expected: user returns to the Test Case List (or previous page); nothing was saved.

**TC-NTC-09: Placeholders** (P3)
- Expected: placeholders are "Title", "Description", "Expected Result", "Test step".

**TC-NTC-10: All created test cases are listed** (P1)
- Steps: create 3 test cases with unique titles (factory, seeded); open the list.
- Expected: all 3 titles are present, each once; the list count increased by 3.

## 7. Execution and exit criteria

- Run order: P1 smoke first (`-g` or tags if introduced), then full suite.
- Exit: all P1 and P2 cases pass; no flaky tests (a pass on retry counts as a defect); every PDF bullet maps to at least one case (see traceability below).
